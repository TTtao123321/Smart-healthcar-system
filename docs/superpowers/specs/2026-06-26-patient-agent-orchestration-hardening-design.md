# Patient Agent 编排收口与安全加固设计

**日期**: 2026-06-26
**状态**: 已确认

## 1. 背景

当前 `patient_agent_backend` 已具备患者登录、聊天、工具调用、挂号查询/创建/取消等基础能力，但主链路仍存在明显分叉和工程化缺口：

- 普通 `/api/chat` 与流式 `/api/chat/stream` 的编排逻辑不一致
- 输入护栏、输出护栏、免责声明、转人工和错误降级没有统一挂在同一执行管线
- 聊天主链路与右侧栏联动逻辑没有完全收口到一套真实业务流程
- HMS、Redis、LLM 等依赖异常时，部分路径仍会暴露为裸 500 或不一致回复
- 测试、日志、CORS 和环境配置仍偏开发态，尚未收敛为可稳定运营的结构

结合当前项目现状，本次采用“两阶段推进”方案：第一阶段先收口患者真实可用主链路，第二阶段补足日志、测试矩阵和配置/CORS 收敛。

## 2. 目标

### 2.1 第一阶段目标

第一阶段聚焦患者侧真实可用能力，目标如下：

1. 将普通聊天与流式聊天统一到同一套编排主链路
2. 稳定支持“查科室 -> 查医生 -> 查排班 -> 确认挂号 -> 查询/取消挂号”
3. 保证聊天与侧栏入口联动到同一套真实业务逻辑
4. 保证 SSE 与普通接口统一走同一套输入护栏、输出护栏、免责声明和转人工逻辑
5. 在 HMS、Redis、LLM、未知异常场景下输出明确降级响应，而不是裸 500
6. 补齐支撑第一阶段稳定性的最小必要测试

### 2.2 第二阶段目标

第二阶段在第一阶段稳定基础上，补齐工程化能力：

1. 建立请求级结构化日志
2. 扩展护栏、HMS client、工具层、聊天集成的测试矩阵
3. 收敛 CORS 策略，去掉生产环境 `*`
4. 对开发、测试、生产环境变量进行分层

## 3. 非目标

本次设计明确不包含以下内容：

- 不重写整个 LangGraph 架构，也不在第一阶段强制引入复杂状态机框架
- 不新增“常用就诊人”“代他人挂号”等多身份能力
- 不在第一阶段扩展 PRD 中未落地的其它业务模块，如院内导航、报告查询、缴费、满意度等
- 不在第一阶段对 HMS Java 后端做大规模架构重构
- 不要求第一阶段完成完整的生产观测平台接入

## 4. 方案概览

本次采用“主链路收口型”方案。

核心思想是：保留当前可用的 LangGraph 和工具体系，不重做底层能力，而是在图执行前后增加一层统一编排服务，把当前分散在 `chat.py`、`nodes.py`、侧栏服务和各类接口里的决策责任收口到一个统一入口。

该方案优先解决以下共因问题：

- 聊天和流式的行为漂移
- 工具失败时不同接口返回不一致
- 免责声明与转人工逻辑重复和遗漏
- 侧栏和聊天入口各自维护一套业务真相
- 后续日志、测试和降级难以统一挂接

## 5. 第一阶段设计

### 5.1 统一编排层

新增统一的 `chat orchestration service`，作为患者对话执行的唯一主入口。

建议抽象出两种对外入口：

- `run_chat_once(...)`
- `run_chat_stream(...)`

两者底层共享同一套执行步骤：

1. 解析请求上下文：`request_id`、`patient_id`、`thread_id`、认证会话
2. 加载历史消息与线程上下文
3. 执行输入护栏
4. 执行业务主链路（LLM + tools）
5. 执行输出护栏
6. 裁决最终回复类型与元信息
7. 保存消息历史与流程上下文
8. 输出普通响应或 SSE 事件

这样做之后：

- `/api/chat` 与 `/api/chat/stream` 不再各自维护一套业务分支
- 侧栏触发的聊天动作与手动输入走同一条业务执行链路
- 免责声明、转人工、工具失败降级都能从统一出口产出

### 5.2 轻量流程上下文

第一阶段不引入重型状态机，而是引入线程级轻量流程上下文，用于承载挂号闭环所需的槽位：

- `intent`
- `selected_dept`
- `selected_doctor`
- `selected_date`
- `selected_work_plan_id`
- `selected_schedule_slot`
- `pending_registration_confirmation`

这些信息由统一编排层读写，并与 `patient_id + thread_id` 绑定。

作用是：

- 避免模型仅依赖自由文本记忆维持挂号流程
- 让“待确认挂号”成为显式状态，而不是模糊对话语义
- 让聊天和侧栏都可消费同一份流程状态

### 5.3 多步业务闭环

第一阶段要求稳定支持以下路径：

1. 查询科室
2. 基于科室查询医生
3. 基于医生/日期查询排班
4. 基于排班时段进入待确认挂号状态
5. 用户显式确认后，调用 `create_registration`
6. 查询本人挂号记录
7. 取消本人挂号记录

主链路约束如下：

- 不允许在没有真实 `work_plan_id / doctor_schedule_id / slot` 来源的情况下直接创建挂号
- 不允许模型跳过“确认挂号”步骤直接执行创建
- 查询和取消挂号始终使用认证会话里的当前患者身份
- 如当前上下文缺少必要槽位，系统必须补问，而不是猜测或编造

### 5.4 侧栏联动

右侧栏不单独维护另一套业务逻辑，而是只做两类工作：

1. 展示统一聚合服务给出的患者摘要信息
2. 把点击动作转换为统一编排层可消费的消息或事件

典型动作包括：

- “查看我的挂号记录”
- “帮我挂这个号”
- “确认挂号”
- “取消这条挂号”

这样保证：

- 聊天与侧栏看到的是同一份挂号事实
- 侧栏发起的挂号确认，本质仍走统一业务主链路
- 后续测试可以把侧栏入口等价视为“另一种聊天触发来源”

### 5.5 统一安全与降级出口

统一编排层应固定执行顺序：

1. 输入护栏
2. 业务执行
3. 输出护栏
4. 最终回复裁决

输入护栏返回结构化判定结果，至少支持：

- `allow`
- `block_with_message`
- `handoff`
- `allow_with_disclaimer`

输出阶段不只负责补免责声明，还要承担以下职责：

- 去除不应暴露给前端的 `<tool_call>` / `<tool_calls>` / 结构化伪调用内容
- 规范工具失败后的最终用户可见文案
- 保证普通接口与流式接口得到一致的最终结论

统一回复裁决结果建议包含：

- `reply_type`
- `message`
- `needs_handoff`
- `disclaimer_added`
- `tool_trace_summary`

其中 `reply_type` 至少区分：

- `normal`
- `disclaimer`
- `handoff`
- `degraded`
- `blocked`

### 5.6 错误降级策略

第一阶段明确收口以下 4 类异常：

#### HMS 异常

- 返回明确的业务系统不可用提示
- 若场景为挂号或取消，必须说明“当前操作未完成”

#### Redis / 记忆异常

- 允许退化为无历史上下文的单轮执行
- 不因为历史读写失败直接返回 500

#### LLM 异常

- 返回固定安全降级文案
- 对医疗相关请求优先提示稍后再试或转人工

#### 未知异常

- 统一返回安全兜底消息
- 不向前端暴露内部堆栈、原始异常文本或系统细节

该策略同时适用于普通接口和 SSE 接口。

### 5.7 与当前 LangGraph 的关系

第一阶段不强制重构图结构，保留：

- `guard_in -> agent -> (handoff | guard_out)`

但需要把“图外”的责任从 `chat.py` 中抽离出来，改为由编排层统一承担：

- 请求上下文构造
- 历史读写
- 流程上下文读写
- 统一异常降级
- 最终输出裁决

必要时对 `nodes.py` 做收口改造，减少普通与流式路径对模型输出的分叉解释逻辑。

## 6. 第二阶段设计

### 6.1 基础日志

建立请求级结构化日志上下文，第一批关键字段如下：

- `request_id`
- `patient_id`
- `thread_id`
- `guardrail_result`
- `reply_type`
- `tool_name`
- `tool_status`
- `hms_error_type`
- `degraded`

日志落点建议如下：

- API 入站日志
- 护栏命中日志
- 工具调用开始 / 结束日志
- HMS 异常日志
- 最终回复摘要日志

### 6.2 测试补齐

第二阶段完整测试矩阵包含：

- 护栏单测
- HMS client 单测
- 工具层单测
- 聊天主流程集成测试

在第一阶段仅补最小必要集，第二阶段继续扩面。

### 6.3 CORS 与配置收敛

不再维持生产环境的全开放 CORS 策略。

按环境拆分为：

- `development`
- `test`
- `production`

配置来源分层为：

1. 代码中的安全默认值
2. `.env.development / .env.test / .env.production`
3. Docker / 部署环境变量覆盖

生产环境要求：

- 不允许 `allow_origins=["*"]`
- 不允许 `allow_credentials=True` 与 `*` 组合
- 白名单必须显式配置

## 7. 测试计划

### 7.1 第一阶段必须覆盖

#### 护栏

- 高危请求被拦截
- 诊断与报告解读被拦截
- 健康话题自动补免责声明
- 需要转人工的请求正确路由

#### HMS client

- 401 自动重登
- 超时 / 4xx / 5xx 异常映射
- `create/query/cancel` 主路径

#### 工具层

- 查排班到确认挂号成功链路
- 查询本人挂号
- 取消本人挂号
- 拒绝取消他人挂号

#### 聊天集成

- 普通接口主链路
- SSE 主链路
- 工具失败降级
- 转人工分支
- 聊天与侧栏入口使用同一业务事实

### 7.2 第二阶段扩展

- Redis 记忆异常退化
- `<tool_calls>` 泄露拦截
- 流式事件一致性
- 输出护栏仅追加一次免责声明
- 复杂多轮流程上下文延续

## 8. 实施顺序

### 第一阶段

1. 抽出统一编排层
2. 统一普通接口与流式接口的主链路
3. 增加轻量流程上下文
4. 把聊天与侧栏入口收口到统一业务链路
5. 收口护栏、免责声明、转人工、降级出口
6. 补齐第一阶段最小必要测试

### 第二阶段

1. 引入请求级日志上下文
2. 扩大 HMS client / 工具层 / 聊天集成测试
3. 收敛配置与 CORS
4. 完成开发 / 测试 / 生产环境变量分层

## 9. 风险与控制

### 风险 1：编排层改动影响现有聊天能力

控制方式：

- 第一阶段保留 LangGraph 与现有工具体系
- 以抽取和收口为主，不做底层彻底改写
- 通过集成测试覆盖普通与流式主路径

### 风险 2：流程上下文引入后与历史消息不一致

控制方式：

- 流程上下文只保存少量关键槽位
- 以“真实工具输出优先”为原则
- 历史上下文丢失时允许退化为重新补问

### 风险 3：流式与普通接口仍出现行为漂移

控制方式：

- 两者共享同一个编排服务
- 最终回复统一由同一裁决结果产出
- 对 SSE 只保留“中间事件展示”差异，不保留业务判定差异

### 风险 4：降级过多导致用户体验变差

控制方式：

- 仅在依赖异常或安全边界触发时降级
- 降级文案明确说明当前操作是否成功执行
- 对医疗场景优先给出稍后再试或转人工建议

## 10. 验收标准

第一阶段验收通过需满足：

1. 患者可稳定在聊天中完成“查科室 -> 查医生 -> 查排班 -> 确认挂号 -> 查询/取消挂号”
2. 右侧栏与聊天入口看到同一份挂号与近期记录事实
3. `/api/chat` 与 `/api/chat/stream` 对同一输入命中同一套护栏和免责声明逻辑
4. HMS、Redis、LLM 异常不再对前端直接暴露裸 500
5. 第一阶段定义的护栏、HMS client、工具层、聊天主流程测试全部通过

第二阶段验收通过需满足：

1. 请求级日志字段完整落地
2. 测试矩阵扩展完成
3. CORS 与环境配置完成按环境收敛

## 11. 推荐结论

推荐按“两阶段 + 主链路收口型”推进。

原因如下：

- 它优先解决当前最影响患者体验和系统稳定性的共因问题
- 它不要求第一阶段进行高风险的大规模架构重写
- 它为后续日志、测试、配置收敛提供了清晰边界
- 它能同时覆盖聊天主链路和侧栏联动，而不会形成两套业务真相
