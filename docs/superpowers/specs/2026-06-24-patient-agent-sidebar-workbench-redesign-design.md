# patient_agent 右侧栏工作台化改版设计

**日期：** 2026-06-24  
**范围：** `patient_agent_frontend` 右侧 sidebar  
**状态：** 已确认

## 1. 背景

当前 `patient_agent_frontend` 右侧区域已经拆分为：

- 上方 `个人信息 + 近期就诊记录`
- 下方 `医院排班`

并且已经接入真实后端接口 `GET /api/patient/sidebar`，前端采用“接口优先、mock 兜底”的方式渲染。

现状的主要问题不在数据链路，而在展示方式：

- 个人信息仍偏“信息卡片堆叠”，业务面板感不强
- 近期就诊记录更像普通内容列表，缺少档案摘要气质
- 医院排班仍然接近“可展开卡片列表”，工作台属性不足
- 视觉风格偏轻演示感，和“正式医疗工作台”目标不完全匹配

因此，本次改造目标是：在不改后端接口和主流程交互的前提下，把右侧 sidebar 调整为更接近正式医院业务系统的专业医疗工作台样式。

## 2. 设计目标

### 2.1 业务目标

- 让上方区域更像稳定、可信的 `患者档案面板`
- 让下方区域更像高效清晰的 `科室排班工作区`
- 在视觉、布局、交互三方面都比当前实现更接近正式医疗系统
- 保留现有 `点击医生 -> 确认挂号 -> onSendChat(...)` 的主链路

### 2.2 体验目标

- 让用户一眼识别“当前患者是谁、基础身份如何、近期就诊情况如何”
- 让用户更快切换科室并查看当天排班
- 减少装饰性“演示卡片感”，增强业务型“面板感”
- 保持右侧信息密度提升的同时，不压垮聊天主区域
- 保证右侧栏所有面板在加载态、空态、mock fallback、长文案和不同科室切换下，边框、圆角和分隔线都不变形

## 3. 确认结论

本次设计已确认以下方向：

- 总体风格：`专业医疗工作台`
- 排班主交互：`按科室切换`
- 上方信息重心：`档案面板化`
- 改动范围：`视觉升级 + 布局重组 + 交互增强`

## 4. 设计方案

本次采用 `工作台重构` 方案。

### 4.1 方案原则

- 保持右侧栏“上档案、下排班”的大结构不变
- 不改变真实接口结构，不追加前后端字段改造
- 重点通过组件结构调整和样式重构完成工作台化升级
- 对当前后端 `GET /api/patient/sidebar` 返回结构完全兼容

### 4.2 不采用的方案

- 不采用“保守升级”，因为仅换皮不足以形成明显工作台感
- 不采用“强业务台/HIS 硬风格”，因为会使聊天页整体过重，损伤当前 agent 产品体验

## 5. 信息架构

### 5.1 右侧总结构

右侧栏继续保持上下两大模块：

1. `患者档案面板`
2. `医院排班工作区`

整体层级改成：

- 顶部信息稳定、规整、可信
- 底部操作密集、切换清晰、动作明确

### 5.2 患者档案面板

上方模块从“信息卡片 + 记录列表”改成真正的档案面板结构：

#### A. 主身份区

置于面板顶部，承担识别和状态表达功能：

- 患者姓名
- 当前身份状态，如 `当前患者`、`已建档`
- 数据来源状态，如 `HMS 数据` / `示例数据`

这一块的目标是让用户第一眼知道：

- 当前右侧信息属于谁
- 数据是否来自真实系统
- 当前处于可操作的正式业务上下文中

#### B. 基础档案区

基础信息改为规整的两列栅格字段区，不再使用松散的卡片式块状排布。

展示字段保持不变：

- 姓名
- 性别
- 年龄
- 手机号
- 身份证尾号

表现原则：

- 字段标签轻、字段值稳
- 左右对齐清晰，像正式业务系统字段区
- 使用细分隔、浅底色、统一字段高度增强秩序感

#### C. 近期就诊记录区

由当前普通内容列表改为 `就诊摘要列表`：

- 每条记录突出日期
- 次级展示科室和医生
- 保持最近 3 条
- 不额外扩展“查看更多”

表现原则：

- 更像“业务轨迹摘要”
- 弱化装饰感，强化信息摘要感
- 保持轻量，不喧宾夺主

## 6. 排班工作区设计

### 6.1 顶部头部

下方模块顶部保留：

- 模块标题 `医院排班`
- 当日日期

但表现改成更明确的工作区头部，强调“今日排班”是一个业务操作面板，而非普通展示卡片。

### 6.2 科室导航

排班主交互保持为 `按科室切换`，但从当前近似按钮/折叠列表改为更明确的工作台导航：

- 导航项清晰区分选中与未选中状态
- 保留医生数量作为辅助信息
- 视觉上更接近“标签导航”或“工作区切换条”

交互原则：

- 默认自动选中第一个有排班的科室
- 切换科室时只刷新当前排班内容，不做花哨动画
- 如果没有任何科室排班，显示业务型空态

### 6.3 当前科室排班面板

当前选中科室下的医生排班区会重做为更强业务层级：

- 医生姓名为主信息
- 职称为次级主信息
- 擅长/简介降为辅助信息
- 出诊时段转为标准化时段标签
- `预约挂号` 为明确动作按钮

设计目标：

- 让用户能快速扫读“哪个医生、什么职称、什么时候出诊、能否立刻挂号”
- 避免卡片内部信息同权，提升排班操作效率

### 6.4 空态与未选中态

当前空态会调整为更贴近业务系统语言：

- 未选中科室：`请选择科室查看今日排班`
- 当前无排班：`当前暂无可展示排班`

这些状态应更像工作台提示，而不是普通内容占位。

## 7. 视觉方向

### 7.1 总体气质

本次视觉方向明确为 `专业医疗工作台`，关键词是：

- 克制
- 清晰
- 稳定
- 可信
- 业务导向

### 7.2 视觉策略

从当前偏轻玻璃感风格，调整为更偏实体业务面板：

- 减弱玻璃态和悬浮展示感
- 加强边框、分区、字段秩序和模块结构感
- 通过留白、分隔、标题层级提升可读性

### 7.3 色彩策略

色彩使用医疗蓝灰体系：

- 主色：稳定医疗蓝
- 辅色：浅蓝灰、中性灰
- 状态色：少量青蓝或轻绿色

约束：

- 不使用偏营销化的高饱和配色
- 不使用明显科技炫光风格
- 不引入强烈玻璃拟态或花哨渐变主导页面

### 7.4 字体与层级

文本层级明确区分为：

- 模块标题
- 字段标签
- 核心数值/姓名/日期
- 辅助说明

目标是让用户在右侧窄栏中仍能快速完成信息扫描。

## 9. 行为设计

### 9.1 保持不变

- 不改聊天主区域
- 不改登录流程
- 不改真实接口结构
- 不改后端字段
- 不改挂号确认后的 `onSendChat(...)` 主链路
- 不新增搜索、筛选、分页、日期切换

### 9.2 本次增强

- 默认自动选中第一个有排班的科室
- 科室导航选中态更明确
- 右侧无排班与未选中状态更业务化
- 医生排班项 hover/active 状态更清楚
- 确认挂号弹窗视觉更统一

## 10. 数据兼容性

### 10.1 保持兼容的字段

本次设计完全基于当前 sidebar 数据结构，不新增后端字段要求：

- `profile.name`
- `profile.gender`
- `profile.age`
- `profile.phone`
- `profile.idCardMasked`
- `recentVisits`
- `schedule.dateLabel`
- `schedule.departments[].departmentName`
- `schedule.departments[].doctors[]`

### 10.2 fallback 兼容

当前前端保留 mock fallback，本次改版后仍需兼容：

- 接口成功时展示真实数据
- 接口失败时展示 mock 数据
- 不因为接口失败导致右侧栏结构错乱

## 11. 风险与约束

### 11.1 风险点

- 右侧区域宽度固定，信息密度提升后容易拥挤
- 如果排班医生信息文案较长，容易破坏工作台的规整性
- 工作台化升级若过度，会和聊天主区域风格脱节

### 11.2 约束策略

- 保持右栏结构稳定，不做大跨度重排
- 优先提升层级和秩序，而不是单纯堆加信息
- 使用克制设计语言，避免把右侧做成“另一个页面”
- 所有卡片、字段区、导航项和弹窗边框都必须采用稳定盒模型，避免因内容撑开导致边框拉伸、圆角失真或分隔线错位
- 需要显式校验长医生姓名、长科室名、加载态提示和空态文案下的边框完整性

## 12. 验证标准

本次改版成功的标准为：

- 个人信息区明显更像正式医院档案面板
- 近期就诊记录明显更像业务摘要而非普通列表
- 排班区明显更像科室导航驱动的排班工作区
- 视觉、布局、交互三方面都有可感知提升
- 不破坏现有接口接线和挂号确认链路
- 前端构建通过
- 右侧所有面板在常规态、加载态、空态和 fallback 态下边框不变形

## 13. 实施建议

建议按以下顺序实施：

1. 先重构 `PatientProfileCard` 与 `RecentVisitsList`
2. 再重构 `HospitalScheduleCard` 与 `DoctorScheduleList`
3. 统一调整 `RegisterConfirmModal`
4. 最后整体收口 `index.css` 的 sidebar 样式和状态样式

这样可以保证：

- 先完成上方档案面板的秩序建立
- 再完成下方排班工作区的主交互升级
- 最后统一视觉语言，降低来回改样式的成本
