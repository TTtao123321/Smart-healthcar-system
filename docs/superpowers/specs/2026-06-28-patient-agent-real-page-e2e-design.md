# patient_agent 真实页面级 E2E 设计

## 背景

当前仓库已经有两类与 `patient_agent` 测试相关的资产：

- 能力基线 benchmark：
  - `benchmark/patient_agent/patient-agent-benchmark.json`
- 前端页面旅程 benchmark：
  - `benchmark/patient_agent/frontend-e2e-cases.md`
  - `benchmark/patient_agent/patient-agent-frontend-e2e.json`
- 现有自动化测试：
  - `patient_agent_backend/tests/...` 下的后端 API、工具、集成测试
  - `patient_agent_frontend/src/...` 下的 Vitest 页面状态与组件测试

这批资产已经能够证明：

- 后端能力边界是稳定且可测试的
- 前端关键页面状态和交互已有组件级与页面级测试支撑

但它们还没有覆盖“真实浏览器访问真实前端页面，并调用本地真实后端服务”的端到端链路。因此，当前仓库仍缺少一套真正页面级、面向患者真实旅程的 E2E 回归体系。

用户本次明确要求将“全面测试”补齐到真正页面级 E2E，且指定采用：

- 浏览器执行真实页面
- 本地真实前端
- 本地真实后端
- 允许为测试补齐 Playwright、测试环境变量、启动脚本和测试数据初始化

## 目标

本次设计目标如下：

1. 为 `patient_agent_frontend` 与 `patient_agent_backend` 建立一套真实页面级 E2E 基建
2. 通过浏览器自动化覆盖当前已形成闭环的患者主旅程
3. 保留真实 HTTP、真实页面渲染、真实浏览器事件和真实 SSE 消费路径
4. 用固定本地测试数据保证回归稳定性和可重复执行
5. 让页面级 E2E 与现有 benchmark case 建立一一映射关系，便于长期维护

## 非目标

本次不做以下工作：

- 不扩展到当前 benchmark 已明确排除的页面能力
- 不把页面级 E2E 退化为纯前端 mock 接口测试
- 不要求首版支持多浏览器矩阵
- 不要求首版直接接入 CI 平台
- 不要求用 Playwright 覆盖所有已有 Vitest 细粒度断言

## 方案总览

本次采用的方案是：

- 真实浏览器：Playwright
- 真实前端：本地 `vite` 服务
- 真实后端：本地 `FastAPI` 服务
- 固定测试数据层：通过后端 `E2E 测试模式` 提供稳定的认证、线程、侧栏、挂号和 SSE 数据

设计原则如下：

1. 页面级 E2E 必须保留真实浏览器与真实前后端调用
2. 稳定性优先于“完全依赖外部真实环境”
3. benchmark 是测试需求源，Playwright 是测试执行层
4. E2E 主要断言用户可感知页面行为，浏览器存储和网络请求只作为辅助证据

## 测试架构

### 1. 浏览器层

Playwright 负责执行真实页面旅程，覆盖以下能力：

- 登录页输入与登录成功跳转
- 聊天页线程恢复与当前线程续聊
- 右侧栏挂号确认与侧栏动作续接线程
- 线程删除成功与失败回滚
- SSE 流式响应最终呈现

Playwright 不直接替代单元测试或组件测试，而是验证多层系统联动后的最终页面行为。

### 2. 前端层

前端继续使用当前 `patient_agent_frontend` 的真实 `vite` 服务启动，不引入专门的前端 mock 页面。页面操作全部作用在真实 DOM 上，包括：

- 输入手机号和验证码
- 点击获取验证码与登录
- 切换历史线程
- 发送消息
- 触发右侧栏挂号确认
- 删除线程

前端仍通过当前 API 层访问后端：

- `axios` 请求 `/api/auth/*`、`/api/chat/*`、`/api/patient/*`
- `fetch` 请求 `/api/chat/stream` 并消费 SSE

### 3. 后端层

后端继续使用真实 `FastAPI` 应用，但增加一套 `E2E 测试模式`。当该模式开启时：

- 认证使用固定测试手机号和验证码
- 线程列表、历史消息、患者档案、侧栏排班、挂号确认结果使用固定 fixture
- SSE 响应返回稳定事件序列
- 删除线程、侧栏失败等分支可以通过初始化数据明确控制

这样既保留了真实后端路由、依赖注入和业务流程，又避免页面 E2E 受 HMS、随机数据或残留 Redis 状态影响。

### 4. 双层运行检查

页面级 E2E 分为两层：

1. 服务启动与健康检查
   - 后端可启动
   - 前端可访问
   - 测试模式可用
2. 页面旅程执行
   - 严格按 benchmark case 跑真实页面回归

这样可以把“服务没起来”和“页面旅程失败”分开定位。

## 运行方式

### 1. 统一执行入口

提供一条统一入口命令，负责：

- 设置 E2E 环境变量
- 启动后端
- 等待后端健康检查通过
- 启动前端
- 等待前端页面可访问
- 执行 Playwright
- 输出报告、截图、trace
- 回收前后端进程

不要求用户手工分别启动多个服务后再执行测试，避免环境漂移。

### 2. 服务启动顺序

推荐启动顺序如下：

1. 准备测试环境变量
2. 重置并播种测试数据
3. 启动后端
4. 轮询后端健康检查
5. 启动前端
6. 轮询前端首页可访问
7. 执行 Playwright

### 3. 进程管理

考虑到首版需要同时管理前端与后端两个服务，建议增加仓库内启动脚本统一控制：

- 端口
- 超时
- 日志路径
- 异常退出处理
- 收尾清理

Playwright 配置可以调用该统一脚本，或者由脚本先拉起服务后再调用 Playwright CLI。

### 4. 首版浏览器范围

首版只要求本地 Chromium 通过，不扩展到 Firefox 或 WebKit。这样可以先把页面旅程和测试数据跑稳，再考虑浏览器矩阵。

## 测试数据与稳定策略

### 1. E2E 测试模式

后端新增独立开关，例如：

- `PATIENT_AGENT_E2E_MODE=true`

该模式只用于本地页面级 E2E，不改变正常开发模式和现有 pytest 测试语义。

### 2. 固定测试身份

预置稳定患者身份作为主回归账号，例如：

- 手机号：`13800138000`
- 验证码：`123456`
- `patient_id`：`12`
- 姓名：`张三`

必要时可扩展辅助患者，但首版不强制。

### 3. 状态重置

提供统一的测试环境重置机制，至少覆盖：

- 验证码缓存
- 登录态
- 线程与消息
- 当前 thread
- 侧栏档案与排班数据
- 挂号待确认状态
- 挂号记录

浏览器侧每条测试前也要重置：

- `localStorage`
- cookie
- storage state

确保服务端状态和浏览器状态同时回到基线。

### 4. 固定业务数据

为以下场景提供稳定 fixture：

- 登录成功
- 历史线程恢复
- 当前线程 SSE 回复
- 右侧栏成功加载
- 右侧栏 fallback 场景
- 侧栏确认挂号并返回 thread
- 删除线程成功
- 删除线程失败

### 5. SSE 稳定策略

SSE 不校验大模型自由生成长文本，而是固定：

- 事件边界
- 关键稳定片段
- 最终落库或渲染结果
- 返回的 `thread_id`

页面级 E2E 主要验证：

- 请求是否成功发出
- 页面是否最终显示回复
- 回复是否渲染到正确线程
- 页面没有卡死在流式中间状态

## 用例范围

首版页面级 E2E 直接映射现有 `patient-agent-frontend-e2e.json` 中已定义的旅程与 case，优先覆盖以下 10 类能力：

1. 登录成功进入聊天页
2. 登录页输入校验
3. 历史线程恢复
4. 当前线程发送消息并消费 SSE
5. 页面刷新后原线程续聊
6. 右侧栏 fallback 展示
7. 右侧栏确认挂号
8. 侧栏动作切换到服务端线程后继续聊天
9. 删除线程成功
10. 删除线程失败回滚

执行优先级按 benchmark 已有优先级分层：

- `P0` 优先作为首批必须通过用例
- `P1` 作为补充回归用例

以下页面能力仍不进入首版页面级 E2E 范围：

- 候诊进度
- 缴费
- 报告下载
- 满意度评价
- 地图导航

原因是当前仓库尚未形成稳定页面闭环，和现有 benchmark 约束保持一致。

## 断言策略

### 1. 主断言

页面级 E2E 以用户可见行为为主要判定标准，例如：

- 页面是否从登录页进入聊天页
- 输入框、线程项、确认弹窗、错误提示是否出现
- 页面刷新后是否仍在原线程续聊
- 侧栏动作后是否切到新的 thread
- 删除失败时 UI 是否回滚
- SSE 回复是否最终显示在页面中

### 2. 辅助断言

浏览器状态和网络请求作为辅助证据使用，包括：

- `localStorage` 中的当前 session
- patient-scoped thread cache
- 请求是否带了正确 `thread_id`
- 请求路径是否正确

这些信息用于增强定位，但不是唯一真相来源。

### 3. 稳定文本断言

不依赖大模型自由文本逐字匹配，只断言稳定边界：

- 页面标题或控件可见
- 固定 toast 文案
- 固定错误提示片段
- 确认弹窗中的稳定文案
- SSE 最终稳定片段

避免因为自然语言措辞波动导致页面 E2E 脆弱。

## 文件结构

### 1. benchmark 作为需求源

以下文件继续作为需求源，不直接放 Playwright 实现：

- `benchmark/patient_agent/README.md`
- `benchmark/patient_agent/frontend-e2e-cases.md`
- `benchmark/patient_agent/patient-agent-frontend-e2e.json`

### 2. 前端 E2E 代码

建议将 Playwright 代码放在前端目录下，便于靠近页面实现与前端依赖：

- `patient_agent_frontend/e2e/`
- `patient_agent_frontend/e2e/fixtures/`
- `patient_agent_frontend/e2e/utils/`
- `patient_agent_frontend/playwright.config.*`

### 3. 启动与编排脚本

建议增加统一脚本，例如：

- `scripts/patient-agent-e2e.*`

职责包括：

- 设置环境变量
- 启动前后端
- 健康检查
- 执行 Playwright
- 收集日志
- 回收进程

### 4. 后端 E2E 支撑代码

后端测试模式、fixture 和 reset/seed 逻辑放在后端仓库内，以保持与真实服务同仓维护，例如：

- `patient_agent_backend/app/...` 中接入 E2E 模式分支
- `patient_agent_backend/tests/e2e_support/` 或相近目录存放 fixture 与测试支撑逻辑

## benchmark 映射规则

Playwright 用例命名、标题和分组必须能回溯到 benchmark case id。

建议规则如下：

- 每个 Playwright spec 文件聚焦一个或一组相关旅程
- 每条测试标题中显式包含 `FE-E2E-xxx`
- 需要时在文件头注释或 helper 中标记对应 `journey`

例如：

- `auth-login.spec.*` 对应 `FE-E2E-001`、`FE-E2E-002`、`FE-E2E-003`
- `thread-recovery.spec.*` 对应 `FE-E2E-004`、`FE-E2E-005`
- `sidebar-registration.spec.*` 对应 `FE-E2E-007`、`FE-E2E-008`、`FE-E2E-009`
- `thread-delete.spec.*` 对应 `FE-E2E-010`、`FE-E2E-011`

## 验收标准

本次设计落地后，应满足以下标准：

1. 一条命令可以完成真实前后端页面级 E2E 执行
2. Playwright 能在真实浏览器中访问真实前端页面
3. 页面请求走本地真实后端，而不是浏览器层 mock
4. 至少覆盖 benchmark 中当前已纳入的主页面旅程
5. 失败时能输出页面截图、trace 和服务日志，便于快速定位

## 风险与约束

### 1. 真实度与稳定性的平衡

如果后端 E2E 模式设计不清晰，页面测试会在“真实服务”与“可重复执行”之间失衡。因此必须明确：

- 什么属于真实链路
- 什么属于测试专用固定数据
- 哪些分支由测试模式显式控制

### 2. 首版不追求覆盖所有细节

现有 Vitest 已覆盖不少细粒度状态逻辑。Playwright 首版应该覆盖患者主旅程和跨层联动，不重复搬运所有组件级断言。

### 3. 本地执行成本

页面级 E2E 会比现有 Vitest 和 pytest 更慢，因此需要：

- 限定首版旅程范围
- 严格控制数据初始化
- 保证服务启动和清理机制可靠

## 后续实施边界

实施阶段需要完成以下几类工作：

1. 引入 Playwright 与配置
2. 增加前后端统一启动与收尾脚本
3. 为后端接入 E2E 测试模式、reset/seed 能力和固定 fixture
4. 将 benchmark 页面旅程映射为 Playwright 用例
5. 增加测试报告、截图和 trace 输出

该设计已明确范围、架构、数据策略、断言策略和交付边界，适合进入实现计划阶段。
