# 智慧医疗号源同步与 Agent 复用设计

## 1. 背景与目标

当前项目已具备以下基础能力：

- `hospital_manage` 后台已具备排班、挂号、患者接诊、病历、处方等核心业务页面与后端接口。
- `patient_agent` 已具备患者登录、侧栏信息聚合、科室/医生/排班查询、挂号确认与取消挂号闭环。
- 基础设施层面已预留 `RabbitMQ`，但当前仓库尚未形成真正的业务事件广播链路。
- 后台 `医疗助手` 页面仍是前端原型，未接入真实 Agent 后端。

本设计用于补齐以下 3 项能力：

1. 号源与挂号全链路双向同步
2. 病历与处方的患者端查询能力
3. 后台医疗助手复用 `patient_agent` Agent 能力

目标是形成两条完整闭环：

- 患者挂号闭环：患者查排班 -> 患者挂号 -> 后台接诊状态同步 -> 排班变更通知
- 诊疗结果闭环：医生接诊写病历/开处方 -> 患者查询就诊结果 -> 最近就诊侧栏联动

同时形成一套可复用的 Agent 服务内核，使患者端与医护端共享编排能力，但严格隔离权限与可用工具范围。

## 2. 设计原则

- 单一数据源：排班、号源、挂号、病历、处方统一以 `hospital_manage_backend/hospital_hms_api` 为权威源。
- 查询实时化：患者端与医护端查询业务数据时优先实时调用 HMS 接口，不以本地副本作为判断依据。
- 事件解耦：`RabbitMQ` 仅承载事务后广播、通知与读模型刷新，不参与主事务判断。
- 复用内核：患者端与医护端共用 Agent 编排框架、工具运行时和通用护栏能力。
- 权限收口：每类端口都通过“会话上下文 + 工具白名单 + 服务端校验 + SQL 条件”的组合做权限控制。
- 分阶段上线：优先补通患者业务主闭环，再逐步扩展到医护端 Agent 复用。

## 3. 范围与非目标

### 3.1 本期范围

- 按三期交付推进：
  - 第 1 期：号源与挂号全链路双向同步
  - 第 2 期：患者端病历与处方查询
  - 第 3 期：后台医疗助手复用 Agent 能力

### 3.2 非目标

- 不在 `patient_agent` 或后台助手侧复制病历、处方、挂号主表。
- 不在第 1 期接入真实短信通道，仅落地站内通知与侧栏联动。
- 不在第 3 期实现“AI 自动写回病历”，只提供草稿辅助生成与一键插入能力。
- 不在本设计内扩展诊断、治疗建议、报告解读等高风险医疗能力。

## 4. 当前系统判断

### 4.1 hospital_manage

- 后台已具备组织管理、医生管理、患者管理、诊费、排班、用户与权限管理能力。
- 患者管理已形成“查询挂号记录 -> 接诊 -> 写病历 -> 开处方 -> 结束就诊”的业务闭环。
- `医疗助手` 页面已具备聊天 UI 原型，但仍返回本地固定文案，未接真实服务。

### 4.2 patient_agent

- 后端已具备患者认证、线程会话、侧栏聚合、科室/医生/排班查询、挂号确认与取消挂号。
- Agent 采用单 `LangGraph` 图 + 规则预路由 + 工具运行时的组合模式。
- 当前工具集主要覆盖科室、医生、排班、挂号，尚未覆盖病历与处方查询。

### 4.3 数据与基础设施

- 号源核心数据已存在于 `doctor_work_plan_schedule.maximum/num`。
- 挂号当前已在 HMS 服务层做“满号校验 + `num` 自增”，但并发控制仍有加强空间。
- `RabbitMQ` 已在配置与 `docker-compose` 中预留，但未形成业务级生产者/消费者代码。

## 5. 总体架构

整体架构采用“权威业务中心 + 异步事件广播 + 多端共享 Agent 内核”的方式。

### 5.1 角色分工

- `hospital_hms_api`
  - 业务主事务处理
  - 权威数据存储
  - RBAC 与接口权限校验
  - 事件发布源
- `RabbitMQ`
  - 广播挂号、排班、病历、处方等领域事件
  - 解耦主事务与通知/读模型刷新
- `patient_agent_backend`
  - 患者聊天入口
  - 患者工具调用与高确定性业务预路由
  - 站内通知与侧栏读模型消费
- 后台医疗助手 Agent 入口
  - 医护自然语言查询入口
  - 医护端工具白名单与权限上下文
  - 病历草稿生成与结构化结果输出

### 5.2 权威源与读模型边界

- 主数据：
  - 排班、时段库存、挂号、病历、处方全部只在 HMS 数据库维护
- 读模型：
  - 患者端侧栏最近就诊
  - 患者端通知中心
  - 后台患者管理状态刷新视图
- 读模型只用于展示与引导，不承担业务判断

## 6. 分阶段设计

## 6.1 第 1 期：号源与挂号全链路双向同步

### 6.1.1 目标

- 以后台出诊管理为唯一号源数据源
- 患者查询排班时返回实时剩余号数
- 挂号成功后原子扣减库存
- 取消挂号后自动回补库存
- 患者端与后台患者管理状态秒级同步
- 后台停诊、调班后患者端实时生效，并向受影响患者发送站内通知

### 6.1.2 数据模型

当前已有：

- `doctor_work_plan`
- `doctor_work_plan_schedule`
- `medical_registration`

设计调整：

- 后台 UI 中将 `doctor_work_plan_schedule.maximum` 明确展示为“号源数量”
- 排班查询与时段详情接口统一返回：
  - `maximum`
  - `num`
  - `remaining = maximum - num`
  - `scheduleStatus`
- 新增或明确业务状态：
  - `doctor_work_plan.status`：`ACTIVE` / `SUSPENDED`
  - `medical_registration.status`：`REGISTERED` / `IN_PROGRESS` / `COMPLETED` / `CANCELLED` / `AFFECTED`

说明：

- 第 1 期不重建库存表，继续复用现有 `maximum/num` 模型。
- 状态字段如数据库尚未覆盖，需要补 schema 与枚举映射。

### 6.1.3 挂号事务设计

挂号创建必须由 HMS 单事务完成：

1. 按 `doctor_schedule_id` 查询时段记录并加行级锁
2. 校验排班存在、未停诊、`num < maximum`
3. 插入 `medical_registration`
4. 更新 `doctor_work_plan_schedule.num = num + 1`
5. 事务提交后发布 `registration.created`

取消挂号必须由 HMS 单事务完成：

1. 校验挂号记录存在且当前状态允许取消
2. 更新挂号状态为 `CANCELLED`
3. 更新时段 `num = max(num - 1, 0)`
4. 事务提交后发布 `registration.cancelled`

该设计替代当前“先查后增”的弱并发控制方式，避免超卖。

### 6.1.4 排班变更设计

后台仍通过出诊管理维护排班，调整入口仍在 HMS。

当发生以下操作时：

- 手动停诊
- 删除可用时段
- 调整时段号源上限
- 移动医生/日期/诊室安排

HMS 需执行以下流程：

1. 更新权威排班数据
2. 识别受影响挂号记录
3. 标记受影响挂号为 `AFFECTED`
4. 发布 `schedule.updated` 或 `schedule.suspended`

患者端查询排班时始终走实时接口，因此排班变更无需等待消费者同步才生效。

### 6.1.5 MQ 事件模型

交换机建议统一为：

- `hms.domain.events`

首批路由键：

- `registration.created`
- `registration.cancelled`
- `schedule.updated`
- `schedule.suspended`

统一事件头：

- `eventId`
- `eventType`
- `occurredAt`
- `traceId`
- `operatorType`
- `operatorId`

挂号事件载荷：

- `registrationId`
- `patientId`
- `workPlanId`
- `doctorScheduleId`
- `doctorId`
- `deptSubId`
- `date`
- `slot`
- `remaining`

排班事件载荷：

- `workPlanId`
- `affectedScheduleIds`
- `changeType`
- `before`
- `after`
- `affectedPatientIds`

可靠性要求：

- 消费端按 `eventId` 做幂等
- 失败消息进入死信队列
- 第 1 期先实现基础告警与人工补偿，不构建完整重放平台

### 6.1.6 两端联动

`patient_agent_backend`：

- 继续通过 HMS 查询接口返回实时排班与剩余号数
- 新增 MQ 消费者，用于刷新患者通知与侧栏读模型
- 首版通知触点限定为站内通知与侧栏

`hospital_manage`：

- 患者管理列表订阅同类事件，刷新接诊状态与挂号状态
- 操作发起方可做乐观刷新，事件消费作为最终一致性校准

### 6.1.7 验收标准

- 并发抢最后 1 个号时只允许 1 人成功
- 患者端排班详情始终返回剩余号数
- 取消挂号后库存自动回补
- 停诊后患者端查询立即不可挂
- 已挂号患者在站内通知与侧栏收到变更提醒
- 后台患者管理状态在秒级内刷新

## 6.2 第 2 期：病历与处方的患者端查询能力

### 6.2.1 目标

- 患者端可查询本人的病历列表、病历详情、处方列表、处方详情
- 支持按就诊时间查看历史记录
- 将“最近就诊”与聊天对话联动
- 严格限制只能查询当前登录患者本人数据
- 对敏感字段返回患者可见版内容

### 6.2.2 工具设计

患者端新增 4 个工具：

- `query_my_medical_records`
- `get_medical_record_detail`
- `query_my_prescriptions`
- `get_prescription_detail`

采用“列表 + 详情”拆分，而不是用两个大接口覆盖全部查询，原因如下：

- 便于 Agent 多轮追问与结果确认
- 便于细粒度权限校验
- 便于脱敏策略分层

### 6.2.3 HMS 患者向接口

建议新增患者端专用接口，而不是直接复用后台管理接口：

- `POST /patient/medical-records`
- `POST /patient/medical-records/detail`
- `POST /patient/prescriptions`
- `POST /patient/prescriptions/detail`

设计原因：

- 后台接口权限模型不适合直接暴露给患者端
- 患者端返回字段需经过脱敏与重组
- 患者向接口可以天然收口为“只允许本人”

### 6.2.4 权限与越权防护

权限校验需要在三层同时落地：

1. Agent 工具层
   - 从当前登录会话中读取 `patient_id`
   - 禁止由调用侧自由传入任意 `patient_id`
2. HMS 服务层
   - 接口内校验病历/处方是否归属当前患者
3. SQL 查询层
   - 查询条件强制附带 `patient_id`

任一层校验失败都必须拒绝访问。

### 6.2.5 脱敏策略

不直接透传后台病历/处方实体，而是新增“患者可见 DTO/VO”。

病历列表返回：

- 就诊时间
- 科室
- 医生
- 主诉摘要
- 记录状态

病历详情返回：

- 主诉
- 现病史摘要
- 体格检查摘要
- 医嘱摘要
- 诊断结论轻脱敏版

处方列表返回：

- 开立时间
- 科室
- 医生
- 处方状态
- 药品数量摘要

处方详情返回：

- 药品名称
- 规格
- 数量
- 频次
- 用药时长
- 患者可见版用法说明

不返回：

- 医生内部备注
- 鉴别诊断过程
- 不适合患者直接查看的内部提醒字段

### 6.2.6 Agent 与侧栏联动

患者端高频意图优先走预路由：

- “我的病历 / 最近病历 / 上次就诊结果”
- “我的处方 / 药单 / 上次开的药”

对话流程：

1. 查询列表
2. 引导用户选择具体记录
3. 调详情工具返回结果

侧栏增强：

- 保留现有 `recentVisits`
- 增加：
  - `hasMedicalRecord`
  - `hasPrescription`
  - `latestResultStatus`

新增侧栏动作：

- `view_recent_medical_record`
- `view_recent_prescription`

侧栏动作继续复用当前“侧栏 -> 结构化消息 -> 同一聊天线程”的交互方式。

### 6.2.7 事件联动

新增事件：

- `medical_record.completed`
- `prescription.created`

事件用途：

- 刷新患者侧栏最近就诊状态
- 生成“新病历/新处方可查看”的站内通知
- 为后续用药提醒、复诊提醒预留基础

### 6.2.8 验收标准

- 患者只能查询本人病历与处方
- 用户提问“我的病历”时可返回历史就诊列表
- 用户点击最近就诊卡片可在聊天中看到详情
- 所有详情均返回患者可见版字段
- 病历完成、处方开立后侧栏与通知可见更新
- 越权访问必须被接口和工具同时拒绝

## 6.3 第 3 期：后台医疗助手复用 Agent 能力

### 6.3.1 目标

- 复用 `patient_agent` 的 LangGraph 编排与工具运行时
- 让后台医疗助手从前端原型变成真实可用能力
- 首批落地两个高频工具：
  - 自然语言查询患者历史病历
  - 病历辅助书写
- 接入后台 RBAC 和数据范围控制

### 6.3.2 复用策略

不复制患者端整套实现，而是抽象出“Agent Core + 渠道适配层”：

- `Agent Core`
  - LangGraph 图
  - 通用聊天编排
  - 工具运行时
  - 通用输出过滤与护栏
- `Channel Adapter`
  - 患者端适配器
  - 医护端适配器

共享内容：

- 图结构
- 工具调用循环
- 预路由机制
- 会话线程模型
- 流式输出协议

差异内容通过上下文注入：

- 当前用户身份
- 当前角色
- 当前工具白名单
- 当前提示词模板
- 当前数据范围

### 6.3.3 医护端首批工具

#### A. 自然语言查询患者历史病历

建议拆成以下内部工具：

- `search_patient_profiles`
- `query_patient_medical_records`
- `get_patient_medical_record_detail`

拆分原因：

- 解决同名患者歧义
- 强化候选确认流程
- 避免模型猜测患者身份

#### B. 病历辅助书写

建议拆成以下内部工具：

- `generate_record_draft`
- `build_insertable_record_payload`

输出内容：

- 现病史草稿
- 体格检查草稿
- 初步医嘱模板

边界要求：

- 第 3 期只生成草稿，不自动写回病历库
- 输出必须明确标注“AI 草稿，仅供医生审核”

### 6.3.4 医护端权限模型

每次请求进入 Agent 前都要构建医护上下文：

- `userId`
- `roleCodes`
- `deptScope`
- `doctorScope`

按角色生成工具白名单，例如：

- 管理员：可查全院范围
- 医生：默认仅查本人接诊患者或科室范围
- 护士：仅开放有限查询，不开放病历草稿生成

权限控制原则：

- 前端不只做按钮隐藏
- Prompt 不只做“请遵守权限”文案约束
- 工具实现必须基于上下文做真实校验

### 6.3.5 Prompt 与护栏区分

患者端 Prompt 重点：

- 导诊与挂号流程
- 不做诊断
- 不编造医院数据

医护端 Prompt 重点：

- 返回结构化病历/就诊记录
- 病历草稿仅作辅助
- 不越权访问患者数据
- 不输出超出工具结果的数据

护栏差异：

- 患者端偏医疗风险提示
- 医护端偏隐私合规与越权访问防护

### 6.3.6 前端接入策略

后台前端首版尽量最小改造：

- 保留现有 `medical_assistant.vue` 聊天布局
- 接入真实聊天接口
- 支持新建会话、历史会话、删除会话
- 支持两类结果渲染：
  - 病历查询结果卡片
  - 病历草稿卡片
- 草稿卡片提供“插入病历编辑器”动作

若病历编辑器尚无联动通道，首版允许通过以下方案兜底：

- 复制草稿文本
- 通过路由参数或共享状态传递草稿

### 6.3.7 验收标准

- 医生输入“查一下患者张三的历史病历”时返回候选患者或结构化病历列表
- 同名患者必须经过候选确认，不能由模型直接猜测
- 医生输入主诉关键词后可生成病历草稿
- 草稿内容明确标注为 AI 生成，仅供审核
- 无权限角色无法调用超范围工具
- 后台医疗助手不再返回前端本地模拟文案
- 患者端与医护端共享同一套 Agent Core，但工具和权限完全隔离

- 区分患者端与医护端 Prompt 模板
- 在请求上下文中注入角色、工具白名单与数据范围

## 9. 风险与缓解

- 并发超卖风险
  - 通过 HMS 单事务与行级锁控制
- 事件重复消费风险
  - 使用 `eventId` 幂等表或幂等键
- 患者越权查看病历风险
  - 使用三层权限校验与 SQL 条件兜底
- 医护端 Agent 越权调用风险
  - 使用工具白名单 + 工具层强校验
- 前端联动复杂度风险
  - 首版优先保留现有页面结构，做最小接入

## 10. 交付顺序建议

推荐交付顺序如下：

1. 第 1 期：完成 HMS 挂号事务增强、事件广播、患者端剩余号数返回、站内通知闭环
2. 第 2 期：完成患者端病历/处方工具、患者向接口、侧栏最近就诊联动
3. 第 3 期：抽象 Agent Core、接入后台医疗助手、上线病历查询与草稿辅助

该顺序能够先打通患者主业务闭环，再在稳定业务能力基础上扩展后台 AI 场景，降低联调与权限改造风险。

## 11. 结论

本设计采用“`HMS` 作为唯一权威源、`RabbitMQ` 做事务后广播、两端共享 Agent 内核但隔离权限”的方案：

- 第 1 期解决排班库存、挂号状态、停诊通知的一致性问题
- 第 2 期补齐患者查看病历与处方的诊疗结果闭环
- 第 3 期复用 `patient_agent` 能力，将后台医疗助手从原型升级为可用功能

最终形成：

- 一条完整的患者门诊闭环
- 一套可复用的 Agent 服务骨架
- 一种以事件驱动完成跨端同步、但不牺牲主数据一致性的系统架构
