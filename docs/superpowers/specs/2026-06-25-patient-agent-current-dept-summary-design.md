# patient_agent 当前科室摘要卡设计

**日期：** 2026-06-25  
**范围：** `patient_agent_frontend` 医院排班模块中的当前科室信息区  
**状态：** 已确认

## 1. 背景

当前 `HospitalScheduleCard` 在医院排班模块中会展示一个 `当前科室` 信息框。

现状如下：

- 当前信息框只显示 `当前科室` 标签和选中科室名称
- 对用户来说，这块信息量偏少，和排班主区域的关联度不足
- 页面高度缩小时，若在这块加入更多摘要信息，还需要继续保证医院排班模块内部可上下滑动浏览

用户已明确提出以下目标：

- 将当前科室信息区改为显示 `科室简介`
- 同时显示 `上午号源数量` 与 `下午号源数量`
- 这块新增信息仍属于医院排班模块内部内容，页面大小变化时需要能在排班模块中上下滑动查看

## 2. 设计目标

### 2.1 业务目标

- 让“当前科室”区域从单纯标题块升级为真正的业务摘要卡
- 帮助用户在查看医生列表前，先快速理解当前科室的概况与号源分布
- 不修改挂号主链路，不增加额外交互状态

### 2.2 体验目标

- 让用户进入某个科室后，一眼能看到该科室的大致简介
- 让用户快速知道上午和下午哪个时段可选号源更多
- 在页面变矮时，这块摘要卡不会再次把医生排班区域压到不可用

## 3. 已确认方案

本次已确认采用 `方案 A：当前科室信息卡增强`。

核心原则如下：

- 保留当前科室信息区的位置，不新增折叠或切换交互
- 前端直接基于当前已拿到的 `doctors` 和 `timeSlots` 推导展示数据
- 当前科室摘要卡仍属于医院排班模块内部内容，并随排班模块一起可滚动浏览

## 4. 数据现状与约束

当前 sidebar 数据结构中，科室级对象只直接提供：

- `departmentId`
- `departmentName`
- `doctors`

医生级对象当前直接提供：

- `doctorName`
- `title`
- `bio`
- `timeSlots`

当前后端 sidebar 模型中没有独立字段：

- `departmentIntro`
- `morningCount`
- `afternoonCount`

因此本次采用 `前端推导` 方案，而不是扩展后端接口。

## 5. 展示方案

### 5.1 当前科室摘要卡内容

当前科室信息区改造后展示以下内容：

1. `当前科室` 标签
2. `科室名称`
3. `科室简介`
4. `上午号源数量`
5. `下午号源数量`

建议信息层级如下：

- 第一层：科室名称
- 第二层：科室简介
- 第三层：上午 / 下午号源统计

这样能保持阅读顺序自然：

- 先知道当前在哪个科室
- 再知道这个科室大概看什么
- 最后知道什么时候号源更多

### 5.2 科室简介推导规则

本次科室简介由前端从当前选中科室的医生简介中推导生成。

规则如下：

- 遍历 `activeDepartment.doctors`
- 取每个医生的 `bio`
- 过滤空值、空字符串和重复内容
- 按原顺序取前若干条有效简介
- 拼接为一段简要摘要文案

约束如下：

- 摘要应控制长度，避免在小高度场景下占据过多空间
- 若没有任何有效 `bio`，则显示 `暂无科室简介`

这意味着它是“当前科室医生擅长方向的聚合摘要”，而不是严格意义上的官方科室介绍。

### 5.3 上午/下午号源数量推导规则

本次 `上午号源数量` 与 `下午号源数量` 由当前科室下所有医生的 `timeSlots` 推导。

统计口径明确如下：

- 遍历当前科室所有医生的 `timeSlots`
- 根据每个时段的开始时间判断属于上午还是下午
- 开始时间 `< 12:00` 计入上午
- 开始时间 `>= 12:00` 计入下午

这里统计的是：

- `可挂号时段数量`

而不是：

- 医生人数
- 剩余真实库存数量

因此文案上应避免误导成真实余号库存。建议使用：

- `上午号源`
- `下午号源`

并默认理解为“当前可展示排班时段数”。

## 6. 排班模块滚动设计

### 6.1 当前科室摘要卡的位置

当前科室摘要卡仍位于：

- 科室导航下方
- 医生排班列表上方

也就是继续属于 `schedule-workbench-panel` 内部的一部分。

### 6.2 小高度场景要求

新增摘要卡后，排班模块必须继续满足：

- 页面变矮时，医院排班模块内部可上下滑动查看全部内容
- 科室导航、当前科室摘要卡、医生列表都属于排班模块内可浏览内容
- 新增摘要卡不应导致医生列表区域完全消失

设计策略如下：

- 摘要卡保持固定在排班内容流中，不单独悬浮
- 摘要卡本身不需要再独立滚动
- 如果排班区域高度不足，由排班模块内部整体滚动链路承担浏览能力

### 6.3 不采用的方案

本次不采用以下方式：

- 不把摘要卡放进科室 tab 项内部
- 不让摘要卡折叠展开
- 不把上午/下午号源统计移动到医生卡片上
- 不新增“查看更多科室简介”交互

这些方案都超出本次范围，且会引入新的状态复杂度。

## 8. 组件职责调整

### 8.1 `HospitalScheduleCard`

本次是主要改动点，新增职责如下：

- 基于当前选中科室推导简介摘要
- 基于当前选中科室推导上午/下午号源数量
- 渲染新的当前科室摘要卡
- 保持现有科室切换与挂号确认逻辑不变

### 8.2 `sidebar-workbench.test.jsx`

需补充或更新测试，覆盖以下行为：

- 当前科室摘要卡会显示简介内容
- 当前科室摘要卡会显示上午号源与下午号源数量
- 样式规则仍保证医院排班模块在小高度下可滚动浏览

### 8.3 `scheduleData.js`

如果现有 mock 数据不足以稳定体现“上午 / 下午都有时段”的统计效果，则补充更明确的测试样本，但不改变当前数据结构的大方向。

## 9. 兼容性要求

本次必须保持以下行为不变：

- 默认自动选中第一个有排班的科室
- 点击医生后打开确认挂号弹窗
- 确认后继续走 `onSendChat(...)`
- 接口失败时仍能使用 fallback mock 数据

同时需兼容以下数据缺省情况：

- 科室没有任何有效医生简介
- 某个科室只有上午时段
- 某个科室只有下午时段
- 某个科室没有任何时段

## 10. 风险与约束

### 10.1 风险点

- 如果简介聚合过长，会明显挤压医生列表可见面积
- 如果“号源数量”文案表达不准，用户可能误解为真实库存余号
- 如果摘要卡样式过重，会削弱排班区主操作内容的可读性

### 10.2 约束策略

- 简介摘要必须控制长度，优先简洁
- 统计口径固定为“时段数”，不包装成库存概念
- 摘要卡视觉上保持轻量，不能压过医生列表
- 延续当前排班模块内部滚动链路，不重新引入整列滚动主行为

## 11. 验证标准

本次改造完成后，应满足以下标准：

- 当前科室区域能显示科室简介
- 当前科室区域能显示上午号源与下午号源数量
- 简介缺失时有明确兜底文案
- 只有上午或只有下午时，统计结果正确
- 页面高度变小时，医院排班模块仍可在模块内部上下滑动查看全部内容
- 不破坏现有科室切换和挂号确认流程
- 前端测试通过
- 前端构建通过

## 12. 实施建议

建议按以下顺序实施：

1. 先补当前科室摘要卡的失败测试
2. 在 `HospitalScheduleCard` 中补前端推导逻辑
3. 更新摘要卡样式并与现有排班滚动链路联调
4. 跑完整测试和构建验证

这样可以保证：

- 先锁定数据推导和展示结果
- 再控制样式影响范围
- 不把这次变更扩散到后端接口层
