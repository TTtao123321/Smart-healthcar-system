# Patient Agent P0/P1 稳定性改造设计

**日期：** 2026-06-28
**范围：** `patient_agent_backend`
**状态：** 已确认，待实现计划

## 概述

当前 `patient_agent_backend` 已具备患者登录、聊天、工具调用、排班查询、挂号创建与取消等基础能力，但高频主链路仍存在三类稳定性风险：

- 挂号确认状态仅保存在进程内内存，服务重启或多实例部署后会丢失
- 高频强流程请求仍主要依赖 prompt 约束和模型自行决策第一步工具，确定性不够
- `nodes.py` 中混合了工具调用循环、错误处理、工具名回退与消息回灌逻辑，已接近运行时层职责

结合当前项目背景，本次改造按“P0 必做 + P1 小幅增强”推进，优先保障患者真实业务主链路稳定，而不是做通用 Agent 架构重写。

## 当前问题

### 1. FlowState 仅为进程内内存

当前 `FlowState` 使用 `InMemoryFlowStateStore` 保存，key 由 `patient_id + thread_id` 拼接得到。

问题包括：

- 服务重启后，待确认挂号状态丢失
- 多实例部署时，线程状态无法共享
- 当前挂号确认链路对进程内状态有隐式依赖，不利于生产稳定性

### 2. 高频主链路对模型决策依赖过强

当前以下高频请求主要依赖 prompt 和工具 docstring 驱动：

- “我的挂号”“挂号记录”
- “取消挂号”“退号”
- 已存在待确认挂号状态时的“就这个”“确认”“选第 2 个”

这种方式在工具数较少时可用，但在医疗业务中存在明显风险：

- 模型可能漏掉应优先执行的工具
- 模型可能在确认态下未正确命中挂号创建工具
- 模型可能在强流程场景下做多余解释，降低用户操作确定性

### 3. 工具运行时职责集中在 `nodes.py`

当前 `agent()` 同时承担：

- 工具调用轮次控制
- 空工具名回退
- 工具执行
- 工具结果 JSON 解析
- 错误回灌
- 继续调用 LLM 的提示构造

这虽然能工作，但继续叠加逻辑会带来：

- `nodes.py` 可维护性持续下降
- 错误分类与日志字段难统一
- 后续测试边界不清晰

## 目标

### P0 目标

1. 将 `FlowState` 持久化到 Redis，保证挂号确认链路跨重启、跨实例可持续
2. 为高频强流程请求增加前置确定性路由，降低对模型第一步工具选择的依赖
3. 补齐挂号主链路的核心回归测试

### P1 目标

1. 对工具调用运行时做小幅收口抽象，减少 `nodes.py` 复杂度
2. 建立最小必要的错误分级和关键链路结构化日志
3. 保持现有前端 SSE 协议和主要接口行为兼容

## 非目标

本次设计明确不包含以下内容：

- 不重写整个 LangGraph 图结构
- 不把全部聊天请求都改为规则引擎或状态机
- 不扩展新的业务域，如缴费、报告、住院、检查预约
- 不调整前端工具事件协议
- 不一次性完成完整平台化治理能力，如熔断、限流、统一观测平台接入

## 方案对比

### 方案 A：稳态优先方案

推荐方案。

核心内容：

- 用 Redis 替换进程内 `FlowState` 存储
- 在聊天执行前增加轻量高频意图前置路由
- 将工具循环抽成小型运行时辅助层
- 补充错误分级、日志与测试

优点：

- 改动范围聚焦在主链路
- 与当前代码结构兼容性高
- 能直接提升挂号链路稳定性
- 风险可控，适合当前项目阶段

缺点：

- 仍保留模型驱动为主的整体编排结构
- 不是彻底的平台级重构

### 方案 B：最小侵入方案

仅做 Redis FlowState。

优点：

- 改动最小
- 回归风险最低

缺点：

- 无法解决高频意图仍过度依赖模型的问题
- 无法缓解 `nodes.py` 的运行时职责膨胀

### 方案 C：重构优先方案

将状态存储、前置路由、工具运行时和工作流编排一次性重构。

不推荐本次采用。

原因：

- 对当前已可用主链路扰动过大
- 需要同时调整更多接口与测试
- 不符合当前“先稳住核心流程”的目标

## 推荐方案

采用“稳态优先方案”。

即：

- P0：`FlowState Redis 化 + 高频意图前置路由 + 核心回归测试`
- P1：`工具运行时小幅抽象 + 错误分级 + 关键日志`

## 详细设计

## 1. FlowState 持久化

### 1.1 数据结构

保留现有 `FlowState` 数据字段不变：

- `intent`
- `selected_dept`
- `selected_doctor`
- `selected_date`
- `selected_work_plan_id`
- `selected_schedule_slot`
- `pending_registration_confirmation`
- `schedule_candidates_by_work_plan`

保持这一点的原因是：

- 不破坏现有 `doctor_tools.py` 与 `registration_tools.py` 的读写语义
- 测试样例和现有挂号确认逻辑可最小改造迁移

### 1.2 存储抽象

新增统一 `FlowStateStore` 抽象接口，至少包含：

- `load(thread_key: str) -> FlowState`
- `save(thread_key: str, payload: dict | FlowState) -> None`
- `delete(thread_key: str) -> None`

保留 `InMemoryFlowStateStore` 作为测试和兜底实现，新增 `RedisFlowStateStore` 作为生产默认实现。

### 1.3 Redis 设计

建议 key 规则为：

- `chat:flow-state:{patient_id}:{thread_id}`

value 为 `FlowState` 的 JSON 序列化结果。

TTL 建议为 24 小时，原因如下：

- 挂号确认链路通常属于短期会话状态
- 足以覆盖患者在当天或隔天短时间内继续完成流程
- 避免待确认状态长期堆积在 Redis

### 1.4 注入方式

应用启动时基于已有 `redis_client` 初始化 `RedisFlowStateStore`，并通过现有全局 getter/setter 注入。

要求：

- 生产与开发默认使用 Redis store
- 测试可继续显式注入 `InMemoryFlowStateStore`
- 若 Redis store 初始化异常，不应直接回退到匿名内存实现而不留日志；需要明确记录降级行为

## 2. 高频意图前置路由

### 2.1 路由位置

在 `ChatOrchestrator` 进入 LangGraph 之前增加“前置路由器”。

执行顺序建议为：

1. 读取历史与线程上下文
2. 检查 `FlowState`
3. 进行高频意图路由判定
4. 命中则走确定性路径
5. 未命中则继续走现有 LangGraph 主链路

### 2.2 本次只处理的高频意图

本次前置路由只覆盖三类高确定性请求：

#### A. 查询挂号记录

典型表达：

- “我的挂号”
- “挂号记录”
- “我挂了哪些号”

处理方式：

- 直接优先进入 `query_registration` 路径

#### B. 取消挂号

典型表达：

- “取消挂号”
- “退号”
- “帮我取消这个预约”

处理方式：

- 优先进入“查本人挂号记录 -> 后续确认取消”的确定性路径
- 若用户未给出具体记录，则先返回真实挂号记录供后续选择

#### C. 挂号确认态

前提：

- 当前线程存在 `pending_registration_confirmation`

典型表达：

- “确认”
- “就这个”
- “选第 2 个”
- “帮我预约这个”

处理方式：

- 优先进入挂号确认路径
- 根据用户表达解析 `slot` 或直接确认当前待确认对象
- 参数不足时回退为明确补问，不猜测

### 2.3 设计边界

前置路由不处理以下场景：

- 科室、医生、排班等一般查询
- 复杂多意图混合请求
- 无明显确定性的自然语言闲聊或健康咨询

未命中的请求继续走模型驱动主链路，避免把系统演进成大而全规则机。

## 3. 工具运行时小幅抽象

### 3.1 抽象目标

不改变当前整体图结构：

- `guard_in -> agent -> guard_out`

但将 `agent()` 内与工具循环直接相关的逻辑下沉到独立运行时辅助层，例如 `tool_runtime.py`。

### 3.2 运行时职责

运行时至少统一处理：

- 工具调用轮次控制
- 工具名归一化与空工具名回退
- 工具执行与结果获取
- 统一 JSON 响应解析
- 追加工具结果上下文
- 异常和空结果分类
- 生成继续调用模型的补充提示

### 3.3 不改变的外部行为

本次不调整：

- LLM 与 tools 的绑定方式
- SSE 向前端输出的 `tool_start` / `tool_end` 协议
- 已有工具函数签名

也就是说，抽象目标是“收口运行时职责”，而不是“重做工具协议”。

## 4. 错误分级与日志

### 4.1 错误分级

本次至少统一以下错误类型：

- `validation_error`
  - 参数缺失
  - 日期格式错误
  - 无待确认状态
- `empty_result`
  - 工具调用成功但无数据
- `upstream_error`
  - HMS 超时
  - HMS 4xx/5xx
  - Redis 读写失败
- `runtime_error`
  - 未知工具
  - 模型工具协议异常
  - 工具结果解析失败

### 4.2 日志字段

关键日志至少包含：

- `patient_id`
- `thread_id`
- `tool_name`
- `tool_status`
- `error_type`
- `route_type`
- `degraded`

其中 `route_type` 至少区分：

- `pre_route`
- `graph_route`

### 4.3 日志落点

至少增加如下日志节点：

- FlowState store 初始化
- FlowState 读写失败
- 高频意图命中与未命中
- 工具调用开始与结束
- 关键挂号路径完成结果

## 5. 测试计划

### 5.1 FlowState 存储测试

至少覆盖：

1. `RedisFlowStateStore` 的 `save/load/delete`
2. key 不存在时 `load` 返回空 `FlowState`
3. `FlowState` 与 JSON 间序列化/反序列化兼容
4. TTL 被正确设置

### 5.2 前置路由测试

至少覆盖：

1. “我的挂号”命中 `query_registration`
2. “取消挂号”命中取消前置路径
3. 存在 `pending_registration_confirmation` 时，“确认/选第几个”命中挂号确认路径
4. 未命中高频意图时，仍进入原有图执行

### 5.3 挂号工具回归测试

至少覆盖：

1. Redis store 下待确认挂号状态仍能正确读取
2. `create_registration` 仍可从确认态补齐缺失参数
3. 成功创建后正确清理对应 `FlowState`

### 5.4 集成测试

至少覆盖：

1. 聊天触发排班详情后设置待确认状态
2. 待确认状态下确认挂号能成功创建挂号
3. 查询挂号和取消挂号主链路不依赖模型首轮自行选工具

## 6. 实施顺序

1. 抽象 `FlowStateStore`，补充 Redis 实现与配置
2. 在应用启动时注入 Redis FlowState store
3. 增加高频意图前置路由器
4. 收口工具运行时辅助层
5. 增加错误分级与关键日志
6. 补齐并运行相关测试

## 7. 风险与控制

### 风险 1：Redis FlowState 引入后影响现有测试

控制方式：

- 保留 `InMemoryFlowStateStore`
- 测试继续显式注入内存实现
- Redis store 单独补自己的单测

### 风险 2：前置路由误判，导致非高频请求被错误拦截

控制方式：

- 只拦截高确定性关键词与确认态场景
- 命中条件保守，不做大而全语义覆盖
- 未命中时保持原有 LangGraph 路径

### 风险 3：运行时抽象引入行为漂移

控制方式：

- 不改前端协议和工具签名
- 优先抽取现有逻辑，不重新设计行为
- 用现有 `test_agent`、`test_tools`、`test_integration` 回归

## 8. 验收标准

本次改造完成后，应满足：

1. `FlowState` 默认保存在 Redis 中，跨服务重启不丢失
2. 挂号确认链路在多轮对话中仍可正确补齐参数并创建挂号
3. “我的挂号”“取消挂号”“确认挂号”不再完全依赖模型首轮工具选择
4. `nodes.py` 中工具循环职责得到收口，相关测试通过
5. 受影响测试通过，且现有 SSE 事件协议保持兼容

## 9. 推荐结论

推荐按本设计直接进入实现计划。

原因如下：

- 它优先解决当前生产风险最高的挂号确认状态持久化问题
- 它只对高频强流程增加确定性，不破坏现有模型驱动主链路
- 它用“小抽象”方式改善运行时结构，适合当前项目阶段
- 它能在有限改动下同时覆盖 P0 必改项与 P1 的最小必要增强
