# patient_agent 右侧栏拆分设计

**日期：** 2026-06-24
**范围：** `patient_agent_frontend`
**状态：** 已确认

## 概述

本次改造目标是在 `patient_agent_frontend` 的聊天页右侧栏中，将现有单一的“今日排班”模块拆分为上下两个业务模块：

- 上方为 `个人信息模块`
- 下方为 `医院排班模块`

其中，个人信息模块首期除基础患者信息外，还需要展示患者近期就诊记录；医院排班模块继续承载按科室查看出诊医生、选择医生并发起挂号意图的交互。

本次仅修改前端，不开发后端接口；但前端数据结构、组件边界和状态组织方式需要为后续对接 HMS 的患者信息表、患者就诊记录、医生出诊信息预留清晰扩展点。

## 当前现状

当前 `patient_agent_frontend` 的右侧栏能力集中在单个 `RightPanel` 组件中，主要问题如下：

- “今日排班”相关 UI、状态、弹窗和 mock 数据集中在 `src/App.jsx`
- 排班数据通过本地常量 `scheduleData` 写死，未和未来的 HMS 数据结构对齐
- 右侧栏当前只展示排班，不展示当前患者上下文信息
- 组件职责耦合，后续若接入患者信息、就诊记录、排班接口，会继续推高 `App.jsx` 复杂度

## 设计目标

### 业务目标

- 让右侧栏同时承载“患者上下文”和“医院排班”两类信息
- 在聊天场景中补充当前患者基础信息和近期就诊记录，帮助挂号和咨询形成上下文
- 保持现有挂号意图入口不变，避免影响当前聊天主流程

### 技术目标

- 将右侧栏从单体模块拆成可维护的独立组件
- 将患者信息 mock 与排班 mock 解耦，便于后续分别对接 HMS 数据源
- 保留当前三栏布局，不扩大改造范围
- 不引入后端依赖，不新增真实接口调用

## 方案选择

本次采用“组件拆分 + mock 数据拆分”的中等改造方案。

### 采用方案

- 保持聊天页三栏结构不变
- 重构右侧栏内部布局，上方显示患者信息与近期就诊记录，下方显示医院排班
- 将右侧栏相关实现从 `App.jsx` 内部单体组件拆为多个独立组件
- 将患者信息与排班信息提取为独立 mock 数据源，字段命名贴近未来接口语义

### 不采用的方案

- 不采用“仅在 `App.jsx` 内局部拆区块”的方案，因为后续接 HMS 时仍会造成单文件膨胀
- 不采用“页面级全面目录重构”的方案，因为超出本次需求范围，会增加不必要的迁移成本

## 布局设计

### 整体结构

右侧栏仍位于聊天页右侧，保留现有侧边栏宽度和外层容器，仅调整内部结构：

```text
PatientSidebar
├── PatientProfileCard
│   ├── 基础信息区
│   └── RecentVisitsList
└── HospitalScheduleCard
    ├── 日期区
    ├── 科室切换区
    ├── DoctorScheduleList
    └── RegisterConfirmModal
```

### 上方模块：个人信息与近期就诊

个人信息模块设计为一张复合卡片，包含两部分：

- `基础信息区`
- `近期就诊记录区`

#### 基础信息区字段

首版展示以下精简字段：

- `姓名`
- `性别`
- `年龄`
- `手机号`
- `身份证号后四位`

这些字段先使用前端 mock 数据，后续用于映射 HMS 患者信息表。

#### 近期就诊记录区字段

首版展示最近 `3` 条记录，每条记录包含：

- `就诊日期`
- `科室`
- `医生`

本次采用紧凑列表样式，不展示诊断摘要、检查状态或处方状态，也不提供“查看更多”交互。

### 下方模块：医院排班

医院排班模块继承现有“今日排班”能力，继续包含：

- 出诊日期展示
- 科室列表切换
- 展开后的医生列表
- 挂号确认弹窗

本次不新增排班搜索、日期切换、筛选和真实挂号接口。

## 组件设计

建议新增如下组件边界：

### `PatientSidebar`

职责：

- 作为右侧栏组合容器
- 组织患者信息和医院排班两个主模块
- 管理右侧栏内部共享的轻量状态

### `PatientProfileCard`

职责：

- 负责渲染患者基础信息
- 负责承载近期就诊记录区
- 不包含任何编辑行为

### `RecentVisitsList`

职责：

- 渲染最近三条就诊记录
- 处理记录为空时的占位样式和文案

### `HospitalScheduleCard`

职责：

- 承载排班日期、科室切换、医生列表和挂号确认状态
- 保持当前“点击科室展开”的交互

### `DoctorScheduleList`

职责：

- 渲染当前科室下的医生卡片列表
- 将点击“预约挂号”的事件向上抛出

### `RegisterConfirmModal`

职责：

- 展示确认挂号信息
- 确认后调用现有 `onSendChat(...)`，将挂号意图发送给聊天主区域

## 数据结构设计

本次不开发接口层，但 mock 数据结构需向 HMS 对接预留。

### 患者信息模型

```ts
type PatientProfile = {
  patientId: string
  name: string
  gender: string
  age: number
  phone: string
  idCardMasked: string
  recentVisits: RecentVisit[]
}
```

### 近期就诊记录模型

```ts
type RecentVisit = {
  visitId: string
  visitDate: string
  department: string
  doctorName: string
}
```

### 排班科室模型

```ts
type ScheduleDepartment = {
  departmentId: string
  departmentName: string
  doctors: DoctorSchedule[]
}
```

### 医生排班模型

```ts
type DoctorSchedule = {
  doctorId: string
  doctorName: string
  title: string
  bio: string
  departmentName: string
  timeSlots: string[]
}
```

### 对接预留说明

- `PatientProfile` 预留给 HMS 患者信息表
- `recentVisits` 预留给 HMS 患者近期就诊记录
- `ScheduleDepartment` 和 `DoctorSchedule` 预留给 HMS 医生出诊信息
- 若未来后端字段命名与前端组件字段不一致，前端通过 adapter 或 mapper 做转换，不直接将后端字段名散落到展示组件中

## 交互设计

### 个人信息模块

- 模块仅做展示，不支持编辑
- 首屏默认展示基础信息和最近三条就诊记录
- 若无近期记录，显示空状态文案与轻量占位

### 排班模块

- 点击科室 tab，展开或收起该科室医生列表
- 点击“预约挂号”，打开确认弹窗
- 点击确认后，继续调用现有 `onSendChat(...)`
- 发送内容仍保持“我要预约挂号：科室 · 医生（职称）”的挂号意图文本

### 保持不变的行为

- 聊天页主布局不变
- 中间聊天区逻辑不变
- 预约确认后仍通过聊天链路承接后续流程

## 视觉与样式方向

- 上方患者信息卡强调“患者上下文”，视觉更稳重、更信息化
- 近期就诊记录采用轻量列表样式，避免与下方排班模块竞争视觉主焦点
- 下方排班模块延续现有蓝白医疗风格，但通过更清晰的分组和间距提升层次感
- 本次不进行激进风格改版，以“结构更清晰、信息分层更明确”为优先目标

## 代码改动范围

- 患者信息 mock 数据文件

- 不开发后端接口
- 不新增真实 HMS 请求

- 不引入路由或页面级重构

## 边界情况

- 患者近期无就诊记录时，显示空状态
- 某科室无医生排班时，显示排班空状态
- 患者信息字段缺失时，允许展示占位文本，不阻塞页面渲染
- 预约确认弹窗中患者姓名仍取当前前端用户上下文；后续若接 HMS，可替换为真实患者信息

## 验证方式

- 右侧栏成功拆分为“个人信息与近期就诊” + “医院排班”两部分
- 上方能展示基础患者信息和最近三条就诊记录
- 下方排班模块仍可展开科室、查看医生并弹出挂号确认框
- 确认挂号后仍能触发现有聊天发送逻辑
- 新增文件与样式调整后无明显构建或诊断错误

## 实施顺序

4. 调整 `index.css`，补充新布局和样式
5. 运行前端构建或诊断检查，确认无明显错误
