# patient_agent 当前功能说明

## 1. 文档目的

本文基于当前仓库中的 `patient_agent_backend`、`patient_agent_frontend`、测试代码和既有参考文档整理，目标是说明 `patient_agent` 目前已经具备、且在代码中可以确认的功能能力与边界。

本文只描述“当前已实现”的能力，不把 PRD 中尚未落地或尚未形成稳定闭环的规划项算作现有功能。

## 2. 总体定位

`patient_agent` 是一个面向患者端的智慧医疗助手，当前主要承担以下职责：

- 患者登录与会话鉴权
- 患者档案读取与基础更新
- 患者侧栏信息聚合展示
- 患者与 Agent 的普通聊天与流式聊天
- 基于医院真实数据的科室、医生、排班、挂号记录查询
- 挂号确认与取消挂号相关流程引导
- 对医疗诊断、报告解读、高危应急等场景做安全边界控制

从系统结构上看，它并不是一个“开放问答型医疗大模型”，而是一个“医院业务工具驱动型 Agent”：

- 前端通过 `/api/chat` 或 `/api/chat/stream` 发起对话
- 后端由 `ChatOrchestrator` 负责加载历史、执行预路由、调用 LangGraph Agent、保存会话
- Agent 在系统 Prompt 约束下调用医院相关工具
- 工具通过 HMS API、HMS MySQL、Redis 返回真实业务数据
- 输出结果经过输入/输出护栏处理后再返回给用户

## 3. 当前核心链路

### 3.1 启动与依赖初始化

后端启动时会完成以下初始化：

- 初始化 HMS 客户端，并登录 HMS 管理端获取调用权限
- 初始化工具集，包括科室、医生、排班、挂号相关工具
- 编译 LangGraph 图
- 初始化 Redis，用于会话、流程状态、短信验证码和对话记忆
- 初始化 MySQL 连接池，用于患者档案读写
- 初始化患者档案服务、认证服务、侧栏服务
- 初始化 Redis 对话记忆

### 3.2 一次普通对话的处理过程

用户发起一次消息后，系统按以下顺序处理：

1. 根据登录态获取 `patient_id`
2. 根据 `thread_id` 读取历史对话
3. 先走预路由 `try_pre_route`
4. 如果命中高确定性意图，则直接调用工具并生成回复
5. 如果未命中，则进入 LangGraph Agent
6. Agent 先做输入护栏检查，再调用 LLM 和工具循环
7. 最终输出经过输出护栏处理
8. 将用户消息和助手回复写回 Redis 记忆
9. 更新线程摘要，供历史线程列表展示

### 3.3 流式对话的处理过程

流式对话在普通对话基础上增加了事件拆分能力：

- 支持输出 `thinking` 事件
- 支持输出 `tool_start` / `tool_end` 事件
- 支持输出最终 `message` 和 `done` 事件
- 会过滤 `<think>...</think>` 中的思考内容与最终可见回复
- 在工具执行完成后，将最终答案作为完整消息返回

这意味着当前前端已经可以展示“思考中、工具调用中、最终回复”三类对话状态。

## 4. 当前已具备的业务功能

### 4.1 认证与患者登录

当前已经具备基础患者认证闭环：

- 发送短信验证码
- 验证码登录
- 基于 Redis 的患者会话管理
- 登出并销毁登录态
- 通过依赖注入对患者接口做登录校验

实现特点：

- 登录成功后，系统会为患者创建 token，并把 `patient_id`、手机号、姓名、登录时间写入 Redis
- 未登录状态下，受保护接口不会返回患者数据
- 支持 E2E 模式，便于测试环境快速登录

### 4.2 患者档案能力

当前已经具备基础患者档案管理能力：

- 按手机号查询患者档案
- 首次登录时自动创建默认患者档案
- 读取当前登录患者档案
- 更新患者基础资料

其中“自动建档”是现有体验的重要一环：

- 如果手机号尚未对应患者档案，系统会自动创建一条默认患者记录
- 默认姓名采用“患者 + 手机号后四位”的方式生成

### 4.3 患者侧栏能力

当前已经具备患者侧栏聚合展示能力：

- 获取患者基础资料摘要
- 获取最近挂号记录
- 获取今日出诊/排班聚合信息
- 支持侧栏动作继续进入 Agent 对话链路

这说明当前 `patient_agent` 不只是一个聊天框，还支持“侧栏信息展示 + 侧栏按钮触发业务动作”的交互模式。

### 4.4 普通聊天与流式聊天

当前已经具备完整聊天闭环：

- 普通聊天接口
- SSE 流式聊天接口
- 基于 `thread_id` 的多线程会话
- 历史消息读取
- 历史线程列表读取
- 删除历史线程
- 患者级线程隔离

当前会话能力的特点：

- 历史消息按 `patient_id + thread_id` 维度存储
- 每个线程会生成标题、最后一条消息、更新时间、消息数量
- 对话轮次会按配置做上限裁剪，避免上下文无限增长
- Redis 中的历史线程和消息都有 TTL

### 4.5 科室信息查询

当前已经具备科室相关能力：

- 查询医院科室列表
- 查询具体科室详情
- 查询科室所在楼层
- 查询科室下的诊室列表
- 对模糊科室名做匹配
- 当匹配到多个科室时，返回候选项供用户进一步选择

这部分能力建立在真实 HMS 数据之上，不依赖模型自行编造医院信息。

### 4.6 医生与排班查询

当前已经具备医生与排班相关能力：

- 按科室查询医生列表
- 按医生姓名查询医生
- 查询医生排班
- 查询科室在指定日期的排班
- 支持“今天 / 明天 / 后天”等日期归一化
- 查询某条排班的时段详情
- 在排班结果和排班详情之间保存候选状态

能力特点：

- 如果医生匹配到多位，会返回候选医生让用户继续选择
- 如果只提供医生名，系统会遍历诊室维度查找可用排班
- 如果只提供科室，系统会按该科室下的诊室查询排班
- 查询排班详情后，会把后续挂号所需上下文写入流程状态

### 4.7 挂号流程能力

当前已经具备挂号流程的核心闭环：

- 识别挂号/预约意图
- 查询医生排班与号源
- 查询具体排班时段详情
- 保存待确认挂号状态
- 用户确认后创建挂号
- 查询当前患者挂号记录
- 取消挂号

当前挂号流程分为两类路径：

#### A. LLM + 工具调用路径

标准路径由 Prompt 约束 LLM 按顺序推进：

1. 询问科室、医生、日期
2. 调用 `query_doctor_schedules`
3. 展示排班与号源
4. 调用 `query_schedule_detail`
5. 用户确认后调用 `create_registration`

#### B. 预路由快速路径

为了提高高确定性场景的稳定性，系统额外实现了规则式预路由：

- “我的挂号 / 挂号记录”会直接走 `query_registration`
- “取消挂号 / 退号”会先查记录，再提示用户按记录 ID 选择
- 如果当前线程里已经存在待确认挂号状态，用户回复“确认”“就这个”“第 2 个”之类内容时，会直接调用 `create_registration`

这部分设计说明当前系统已经把“高确定性业务动作”从纯模型推理中抽离出来，提高了挂号确认链路的可控性。

### 4.8 侧栏触发挂号确认

当前已经具备从患者侧栏继续完成挂号动作的能力：

- 侧栏动作接口会接收 `action + thread_id + payload`
- 当前仅开放 `confirm_registration`
- 侧栏动作会被转换成一条结构化消息，再送入同一套 `ChatOrchestrator`
- 因此侧栏交互与聊天线程共享上下文

这意味着：

- 用户可以先在聊天中完成挂号意图和候选确认
- 再在侧栏中执行确认挂号
- 系统仍然能够识别当前线程里的待确认状态并完成挂号

## 5. 当前 Agent 能力特征

### 5.1 工具驱动而非自由生成

当前 Agent 的回答高度依赖工具返回结果，系统 Prompt 明确要求：

- 查询型问题必须调用相应工具
- 回复内容只能使用工具返回的真实字段
- 工具失败或空结果时必须如实告知
- 禁止编造科室、医生、诊室、地址、楼层、职称等信息

### 5.2 支持多轮工具调用

当前工具执行运行时已经具备多轮工具调用能力：

- 模型返回 `tool_calls` 后，系统可以连续执行多轮工具
- 最多支持 5 轮工具回合
- 每轮工具结果都会回灌给模型，要求其基于真实数据继续推理
- 如果模型输出空工具名，系统会按关键词做有限回退恢复

这说明当前 Agent 已具备“多步查询 -> 汇总答复”的能力，而不是单次工具调用后立即结束。

### 5.3 已接入请求上下文

当前请求上下文已贯穿到工具层：

- 工具可以读取当前真实 `patient_id`
- 工具可以读取当前 `thread_id`
- 挂号、查挂号、取消挂号都基于登录患者身份执行
- 流程状态与线程强绑定，避免跨线程污染

## 6. 当前记忆与状态能力

### 6.1 对话记忆

当前系统使用 Redis 保存对话记忆，已具备：

- 按患者和线程加载历史消息
- 保存完整对话消息
- 限制最大对话轮次
- 保存线程摘要信息
- 列出线程
- 删除线程

### 6.2 线程级流程状态

除普通聊天记忆外，系统还实现了线程级业务状态存储，用于挂号等流程型任务。

当前已存储的关键状态包括：

- `pending_registration_confirmation`
  - 待确认挂号信息
  - 包括 `work_plan_id`、`doctor_schedule_id`、`doctor_id`、`dept_sub_id`、`appointment_date`、`slot`
  - 以及可选时段列表 `schedule_options`
- `schedule_candidates_by_work_plan`
  - 排班候选映射
  - 用于在查排班详情时补全缺失的医生、诊室、日期信息

这说明当前 `patient_agent` 已经具备“会话记忆”之外的“流程状态记忆”，能够支持多轮挂号确认。

## 7. 当前安全护栏能力

### 7.1 输入护栏

当前输入护栏已经覆盖以下场景：

- 高危应急识别
- 诊断请求拦截
- 检查/化验报告解读拦截
- 用户主动要求转人工
- 健康话题免责声明标记

处理策略如下：

- 高危应急：直接拦截，并提示拨打急救电话，同时转人工
- 诊断请求：拒绝诊断，保留就医流程服务定位
- 报告解读：拒绝解读，建议咨询医生
- 转人工请求：进入人工客服路径
- 健康话题：允许回答，但会触发免责声明逻辑

### 7.2 输出护栏

当前输出护栏已经覆盖以下能力：

- 检测疑似医疗建议性话术
- 检测疑似编造信息
- 自动追加免责声明
- 避免重复追加免责声明

因此当前系统并不是简单把 LLM 输出原样返回，而是对医疗风险和幻觉风险做了额外保护。

## 9. 当前已形成闭环的能力范围

结合代码、测试和 benchmark，可以认为当前已经形成稳定闭环的能力主要包括：

- 患者认证与会话管理
- 患者档案读写
- 患者侧栏数据聚合
- 聊天、流式聊天、线程管理
- 科室查询
- 医生查询
- 排班查询
- 排班详情查询
- 挂号确认
- 挂号记录查询
- 取消挂号引导与执行
- 安全护栏

## 10. 当前明确的边界与未稳定闭环能力

以下能力虽然可能出现在 PRD、设计描述或产品规划中，但从当前代码实现看，尚未形成稳定闭环，不能视为 `patient_agent` 已具备功能：

- 院内导航
- 候诊进度
- 报告查询结果展示与 PDF 下载
- 缴费引导
- 用药提醒
- 复诊提醒
- 满意度评价
- 运营后台与知识库管理
- 严格规则化的症状分诊引擎
- 严格规则化的医生推荐引擎

另外，当前系统还有几个明显边界：

- 不提供疾病诊断
- 不提供治疗方案和用药建议
- 不解读检查报告
- 不评价医生水平
- 不允许脱离工具编造医院业务数据

## 11. 总结

从当前仓库实现来看，`patient_agent` 已经不是一个原型级 Demo，而是一个围绕“患者登录 -> 查询医院真实数据 -> 完成挂号相关流程 -> 留存线程与状态 -> 加入安全护栏”的可运行患者服务 Agent。

它当前最成熟的能力集中在三条主线：

- 患者身份与档案管理
- 聊天式就医流程查询与挂号流程闭环
- 线程记忆、流程状态和安全护栏的工程化支撑

如果后续要继续扩展，最自然的方向通常会是：

- 扩展更多医院业务工具
- 把更多高确定性流程从纯 LLM 路径中抽成预路由或规则编排
- 完善侧栏动作与聊天流的联动
- 补齐当前尚未稳定闭环的 PRD 能力项
